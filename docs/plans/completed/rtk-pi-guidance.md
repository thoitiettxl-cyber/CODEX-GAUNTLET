# Integrate RTK guidance into Pi without automatic rewriting

Harness story: `TERMUX-004`

## Current context

RTK `0.43.0` is already installed as the pinned native Android AArch64 binary
at `~/.local/bin/rtk`. The deployed config, provenance, privacy posture, Codex
policy, and Harness registration pass `scripts/termux-control rtk status
--json` and `scripts/termux-control rtk doctor --json`.

Pi `0.82.1` is installed through the repository-owned Termux launcher topology.
`/data/user/0/com.termux/files/home/.pi/agent` and
`/data/data/com.termux/files/home/.pi/agent` resolve to the same directory.
The Pi process can resolve and execute `rtk 0.43.0` through its glibc runner.
No Pi package, `~/.pi/agent/extensions/rtk.ts`, or
`~/.pi/agent/APPEND_SYSTEM.md` is currently installed.

The upstream `hooks/pi/rtk.ts` on both RTK `v0.43.0` and the inspected
`develop` branch is the same thin automatic rewrite extension generated by
`rtk init -g --agent pi`. It delegates every Bash tool call to `rtk rewrite`.
The installed rewriter was observed rewriting shell composition such as
`cargo test && cargo build` and `cargo test | tee test.log`, which conflicts
with the repository accuracy contract requiring those shapes to remain raw.

## Outcome

Give Pi the same accuracy-first RTK operating posture as Codex:

- RTK policy is loaded automatically into normal Pi sessions.
- Pi deliberately prefixes only supported individual noisy commands when a
  compact orientation result is useful.
- Exact readers, machine output, shell composition, mutation, final Git
  review, control-plane commands, and canonical verification remain raw.
- RTK output never becomes executable pass evidence.
- No automatic Bash rewrite hook is installed.
- The repository detects Pi policy drift without printing policy or
  secret-bearing bodies.

## Approach

1. Reinspect live Pi and RTK state before mutation, including the exact
   `APPEND_SYSTEM.md` and extension targets. Stop on unexpected drift.
2. Keep the canonical RTK operating rules runtime-neutral without weakening
   any raw, privacy, telemetry, tracking, tee, or recovery requirement, while
   preserving the byte-matched protected Codex deployment.
3. Extend RTK inventory and product/runbook contracts with a Pi policy target
   while keeping `automatic_rewrite: false`.
4. Extend `scripts/rtk_control.py` status and doctor surfaces to verify the Pi
   policy target and the absence of the prohibited automatic RTK Pi extension.
   Do not print deployed instruction bodies.
5. Add synthetic unit and integration coverage for materialization, drift,
   privacy, and no-auto-rewrite behavior.
6. After explicit authorization for user-global mutation, materialize the
   reviewed policy through Pi's documented global
   `~/.pi/agent/APPEND_SYSTEM.md` mechanism. Preserve any pre-existing content
   or stop for review rather than overwrite it.
7. Reload or restart Pi, run focused proof, run the canonical repository gate,
   and review the final raw diff and user-global metadata.

## Decisions

- Match Codex's guidance-only process, not upstream Pi automatic rewriting.
- Keep `docs/product/rtk-termux.md`, `config/rtk/RTK.md`, inventory, control
  code, and synthetic fixtures as repository truth.
- Use Pi's documented `~/.pi/agent/APPEND_SYSTEM.md` discovery surface because
  Pi does not document Codex-style `@file` expansion for arbitrary policy
  files.
- Keep the RTK binary and privacy config shared; do not install another binary,
  Pi package, or generic Linux artifact.
- Preserve the existing canonical policy bytes because the deployed protected
  Codex target already matches them exactly. The operating rules are shared
  with Pi even though the historical heading still names Codex.
- Keep telemetry and tracking disabled, the tracking database sink at
  `/dev/null`, and failure tee private and bounded.
- Treat `$rtk-tune` as optional explicit maintenance capability, not ordinary
  runtime routing and not a prerequisite for Pi parity.

## Risks

- `APPEND_SYSTEM.md` is a shared Pi customization surface. Overwriting a future
  user file would destroy unrelated prompt content; stop on drift or implement
  a reviewed managed-section strategy.
- Copying policy without inventory and drift checks would create two divergent
  sources of truth.
- Installing upstream `hooks/pi/rtk.ts` would silently change the documented
  `automatic_rewrite: false` boundary and can filter shell composition.
- Filtered test output can hide decision-critical details and must never be
  accepted as pass evidence.
- The worktree already contains unrelated uncommitted Pi/RG changes; do not
  discard, restore, or silently absorb them into this story.

## Recovery

- Before any authorized Pi global write, record target existence, mode, size,
  and checksum without printing bodies. Create a private exact backup when a
  target already exists.
- If a newly created Pi policy fails, remove only the exact new
  `~/.pi/agent/APPEND_SYSTEM.md` after confirming it did not pre-exist, then
  reload or restart Pi.
- If a prior target existed, restore only its exact private backup and confirm
  its checksum.
- Never modify or remove `~/.pi/agent/auth.json`, model credentials, sessions,
  Pi core release symlinks, or the RTK binary as part of this story.
- Harness recovery uses the reviewed semantic changeset; never copy a live
  `harness.db`.
